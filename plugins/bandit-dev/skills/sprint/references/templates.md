# 🧾 Shapes and titles

Part of `bandit-dev:sprint`. A note's kinds, fields, status, places, storage and inbox rules belong to bandit:notes; card sections belong to bandit:tasks. This file only fixes the sprint-specific shapes. A fixed shape is justified because other steps and chats read these records.

Contents: Papers · Notes file · The sprint in the app · Step comment · Plan note · Brief change log · Execution prompt · Wave note · Ledger · Wave report · Pre-sprint estimate · Sprint data · Debug card · Approval line · Report

## Papers

A sprint's papers are notes, written and read through bandit:notes in the project's storage (`references/model.md` there → Which storage; `references/other-skills.md` → Who writes what). `{project}` is the project slug, `{name}` the sprint name in kebab-case.

- **On the app's Notes:** each paper is a note on the project's board (`board:` in the Project Context) with the tag `sprint-{name}` and the kind below, written straight in: filed with `notes_file` into the column the sprint's cards sit in (the first card's in run order when they sit in several). The sprint's papers are the board's notes with that tag (`notes_list`, and with `archived: true` once the sprint is closed). No folder.
- **In the vault:** each paper is a file named `{title}.md` in the sprint folder `Projects/{slug}/sprint-{name}/` (bandit:notes `references/conventions-vault.md` §1 → Sprint folders), as before.

| Paper | Title | Kind |
|---|---|---|
| Plan | `{project}-sprint-{name}-plan` | `plan`, with no card link (Plan note) |
| Execution prompt | `{project}-sprint-{name}-handover-prompt` | `reference` |
| Ledger | `{project}-sprint-{name}-progress` | `reference` |
| Wave note | `{project}-sprint-{name}-wave-{n}`, one per wave (written at plan step 12, Wave note below) | `reference` |
| Handover report | `{project}-sprint-{name}-handover-report` (created by the execution chat) | `reference` |
| Wave report | `{project}-sprint-{name}-wave-report` (rebuilt at the end of every wave, Wave report below) | `reference` |
| Review record | `{project}-review-sprint-{name}-YYYY-MM-DD` (written at step 11 from the `plan-reviewer` agent's report) | `log` |
| Sprint targets note | `{project}-sprint-targets`, one per project, in the project's place for planning documents, not tagged with a sprint (the home of a project's targets, keyed by measure name; a project's own, so they change without a release) | `reference` |
| Briefs | one per card, bandit:notes brief naming (`references/plan.md` step 12) | `brief` |

**Every paper is created with all its headings**, `_Pending_` under each heading not yet written, so every later write changes one section (bandit:notes create without a duplicate, then its edit by section). A paper the storage refuses as too large is bandit:notes' refusal (`references/storage-app.md` → Refusals): split on the user's yes, nothing cut.

**Files that are not text** are not notes. On the app's Notes they are data files in `.sprint/` at the root of the repository the helper runs from, git-ignored (say so when the repository's `.gitignore` lacks it); in the vault they stay where they were:

| File | App's Notes | Vault |
|---|---|---|
| Sprint data file | `.sprint/{project}-sprint-data.csv`, one per project (rebuilt at the end of every wave and at close, Sprint data below) | `{project}-sprint-data.csv` in `Projects/{slug}/planning/` |

## Notes file

The sprint's scripts never read a storage: `check_sprint.py`, `sprint_data.py` and `sprint_targets.py` read the project's **notes file**, `.sprint/{project}-sprint-notes.json` at the root of the repository the helper runs from (git-ignored, in either storage). The helper builds it through bandit:notes, **whole, right before every run** of those scripts (plan step 1's closed-sprint check and step 12, every wave end, `run`'s wave check, close step 4); it is never edited by hand, and a run on an old copy proves nothing.

- **Shape:** one JSON object, `{"project": "{project}", "built": "{time, ISO 8601 with its offset or Z}", "notes": [{"title", "kind", "status", "tags", "cards", "text"}, …], "titles": [...]}`; `tags` and `cards` are lists (`cards` holds the linked cards' short ids), `text` is the whole text. A note read from the vault whose frontmatter does not parse also carries `"frontmatter_error": "{the parser's first line}"` (SP4); a note on the app's Notes never does, nor does the user's own inbox note with no frontmatter or status `inbox`.
- **Which notes**, read whole into `notes`: every paper of every sprint of the project, live and archived (the notes tagged `sprint-{name}`), each sprint's WBS note (`{project}-sprint-{name}-wbs`), the targets note, and **every brief of the project whatever its tag or place**, the Inbox and the project's root included, so a brief left outside its sprint (SP2) or a second brief of a card (SP6) is seen. **`titles`** holds the title of every other note of the project, so a title held twice is seen (SP3).
- **Every sprint, never only the one at hand:** a note is read whole by its title or its kind, never by its tag alone, so a paper of any sprint, live or archived, is in `notes` even when it lacks its sprint's tag, and never only in `titles`.
- **Tags exactly as stored:** the builder never adds a sprint tag a note lacks, never drops one, and never infers one from a title (the vault's sprint-folder tag below is the one exception). The checker then names a paper without its sprint's tag, and a `sprint-{name}` tag when no paper of that sprint exists (SP1); the fix goes through bandit:notes, never into the file.
- **In order:** `notes` sorted by title, each note's `tags` and `cards` sorted, `titles` sorted, so two builds of the same notes differ only in `built`.
- **On the app's Notes:** `notes_list` of the project's board (its Inbox included), then again with `archived: true`; a row carries the kind, title, status and cards but no tags or text, so each note whose title starts with `{project}-sprint-` or `{project}-review-sprint-`, and each note of kind `brief`, is read with `notes_get` (its `tags` and `body`); every other row's title goes into `titles`.
- **In the vault:** the same from `Projects/{slug}/` (its root, sprint folders and `planning/`), `_archive/Projects/{slug}/` and, for briefs, the domain's `_inbox/`, read through bandit:notes, by the field mapping: `title` the filename without `.md`, `kind` the `type`, `status` the frontmatter's (`archived` for a note under `_archive/`), `tags` the frontmatter's plus `sprint-{name}` for a note in a sprint folder, `cards` the `board-task` of a brief, `text` the body without its frontmatter; every other note's filename without `.md` goes into `titles`.
- **The Stop hook** runs only in a chat that used the sprint helper (a Skill call or a typed `/bandit-dev:sprint` command, or a tool call on this file; the skill's name in the chat's skill and agent lists is not use) and reads this file for the repository's own project (its Project Context): a missing file, or one built before the session began, is a notice; an error in a file built in the session blocks the stop once.

## The sprint in the app

One sprint on the home board (`manage_sprints`, bandit:tasks `references/board.md` → Tags): `name` =
`{name}`, `expectedDate` = the sprint date, `papersUrl` = where the papers are, as text (the app takes
any text there): on the app's Notes `{board} notes, tag sprint-{name}`; in the vault the sprint
folder's path (`MyNotes/{D}/Projects/{slug}/sprint-{name}/`); its cards = the batch in its waves (plan step 12 sets each card's wave: `add_wave`, `set_wave`;
the run order is wave, then the plan's order inside a wave), the plan's lands-after pairs as `link_tasks` kind `lands_after`,
and the debug card alone in the last wave. Status: Planning at step 1, Ready to execute at step 12, then
`references/execute.md` → Sprint status; while it runs, its run state (running, paused, replanning:
`references/execute.md` → Run state). The app draws the sprint's map on its sprint page. Nothing else is
stored in the app: goal, batch table, cross-card notes, risks and decisions live in the plan and the ledger.

## Step comment

The step's row in the ledger's **Plan steps** table: the done date and the evidence, `{what was found and decided, with ids}. {Fix rows applied or open.}` A few lines' worth in one cell; longer findings go in the Milestone log, and the cell names them. Step 9's cell also holds each Batch card's build-step count, `{card id}: {n} steps` (planning's sub-tasks; `Gate:` lines and the approval line not counted); the checker's SP13 reads it.

## Plan note

Kind `plan`, status `active`, no lane and no card link: the sprint's tag in place of the card (in the vault `sprint` = the sprint's name), related to every brief (bandit:notes conventions §13, sprint records). Body: H1 title; summary line; **Summary** (counts, wave table with reasons and each wave's time estimate: Pre-sprint estimate); **WBS** (the batch's work breakdown note, named by its title, and the wave split it supports); **How every card is executed** (branches, working loop, never-in-parallel, migrations, regenerated artefacts, credentials, live checks create and remove their own test data and never alter existing records, through `/bandit-dev:testdata` when the project has a `testdata` section (Test data in `plan.md`), hard rules, design rules); one section per card (Approach, Tests, Docs, Verify first, Verification table of acceptance against proof; a card with a `Design:` line adds the row "matches the design handover", naming the screen sizes to compare); **Migration tail** (the tail the sprint starts from, then one row per wave: the tail it must start from and the numbers it adds; `execute` checks it); **Final push** (`plan.md` step 7); **Cross-card items**; **Gaps answered by convention** (one line per gap: card, gap, the convention that answered it); **Items to register** (each item the sprint owes, with its trigger: `(trigger: wave {n})` or `(trigger: debug)`; a change to the repository is never left for the close, the release or after the sprint, so the release ships all of the sprint's work; checker SP14); **Risks and rollback**; **Related**. After approval the plan stays stable; changing facts go in the ledger.

## Brief change log

Each brief ends, before Related, with `## Change log`: one dated entry per planning pass, saying what changed and why (requirements added or removed and the finding behind it, decisions, answered questions, a split). Keep the old wording out of the body; keep the reason in the log. On the app's Notes a brief then gets `## Conclusions`, after Change log and before Related, when its card is completed: a heading the brief was not created with, added by a whole-text save (bandit:notes `references/conclusions.md` → Writing the section).

## Execution prompt

Model: the latest sprint's execution prompt among the project's papers (an archived one once that sprint is closed: Papers), adjusted to the shape below. Copy its structure and replace the sprint content. Required sections: how the user starts or resumes a chat (one paste per wave, `/bandit-dev:sprint execute {sprint} wave {n}`); context (project, where the sprint's papers are and which they are); goal; **read first every session** (the wave note of the wave being run, named by its title, the repository documents its First reading names and the wave's cards; never the whole plan or ledger: `execute.md` → Start); authority and stop-lines (including the Test data rule from `plan.md`: live checks and tests create and remove their own data, through `/bandit-dev:testdata create` and `clean` when the project has a `testdata` section, never alter existing records, and a case skipped for lack of data is a failed check; explicit approval to implement; the authorised push of `development` (a reinforced line saying an older "never push" note or memory is superseded); never touch the main branch, deploy, force-push, run credential scripts, touch production, edit the user's verbatim documents or rules, override the Spec lock, write to cards outside the sprint, mark anything complete or approved); autonomy (no questions about what the Spec, the plan, its Gaps answered by convention block or the project's rules already answer; a gap none of them answers stops that card: `Paused: {reason}` in the ledger's Status line and Needs the user, and one plain question to the user with a recommendation (`execute.md` → Needs a decision); hard blockers stop the wave as before); the wave cycle (branch, verify-first, implement with tests, gates in order, report section, merge into local development, board comment, ledger; at wave end, mark that wave done in the ledger's Waves table with its evidence); the ledger rules (update after every milestone, one section at a time through bandit:notes, read right before each write, resume reconciles repo and ledger); the handover report (per card: what you get, how to test it, how we tested it, limits and the conventions applied, where it lives, if it breaks; then regression list, needs-the-user list, bug log); the final message (ten lines at most, one wave per run); a debug and close section that only points to `references/debug.md` and `references/close.md` (no procedure copied); a wave and card reference table.

The execution prompt must carry the No leftovers rule (`references/homes.md` → Leftovers) in its wave cycle, and in it the design comparison: for a card with a `Design:` line, the UI check's brief names the design handover (its files are found through the `Handover:` line: the design card's, reached through the build card's `blockedBy`, or the build card's own Source when there is no design card) and asks for one comparison inside the same UI-check launch, after the screen passes its working checks (layout, the handover's maps and recorded decisions, at the screen sizes the handover covers); the result goes in the card's report section as "matches the design handover" or one line per difference with the handover line it breaks, and a difference left in is Different in the wave report; a card with no `Design:` line gets no comparison. The wave cycle also carries two marks the wave report counts on: each card starts with the shell command `echo CARD-START {card}`, and a code review run in the background is briefed with the commit to read and reads that commit's files (`git show {commit}:{path}`), never the working copy. It carries the search rule (`execute.md` → The wave, step 4c) and, beside it, the measure the next sprint reads: the shell output a wave agent takes in, in characters, counted from its chat log (baseline 501,000 a wave; target at most half). It also carries the wait: no merge, card move or ledger line before a gate's verdict is back, and no end of the turn while a gate agent runs (`execute.md` → The wave, step 4b).

**Gate order.** The wave cycle's gates section carries these lines word for word, so each card goes through each gate once:

> Per card, in this order: code review and every fix first; then one browser check (when UI changed); then one full check, last, after the card's notes and status are committed, only when `code_changed.py` says "full check: needed"; then merge. A browser check never starts while code review is still open.
> A change of only docs, notes or comments runs no full check: `python3 ${CLAUDE_SKILL_DIR}/scripts/code_changed.py` decides, and its line goes in the card's notes in place of the check.
> After the merge, the trunk check counts as done when the project's full check prints "already passed": no second full run when only notes changed.

## Wave note

One note per wave, written at plan step 12, once the review's changes are in the plan, so a wave starts from its own part of the papers and not from the whole plan and ledger (`execute.md` → Start). Kind `reference`, the sprint's tag (in the vault `sprint` = the sprint's name). Everything in it is **copied word for word** from the plan and the ledger, never summarised or reworded. The plan and the ledger stay whole and stay the source: where a wave note differs, they win, and a change made to the plan after step 12 is copied into the wave notes it touches in the same step. A wave reads its note and never writes it. Sections, in this order; one with nothing to hold is left out:

- `# Sprint {name} — wave {n}`, then the summary line.
- `## Cards`: the ledger's Batch rows of this wave's cards (their `Blocked by` included), the plan's `Lands after:` pairs that name them, each card's branch, and the At a glance lines that do not change (`Sprint record:`, `Committed:`, `Debug card:`, the sprint date, where the papers are).
- `## How every card is executed`: the plan's section, whole.
- One `## {card} — {title}` section per card of the wave: the plan's section for that card, whole, then every line of the review's changes that names the card.
- `## Migration tail`: this wave's row, or "No migrations".
- `## Final push`: the plan's section, only in the wave that carries the push.
- `## Cross-card items`, `## Gaps answered by convention`, `## Items to register`, `## Risks and rollback`: the plan's lines that name one of this wave's cards or the whole sprint.
- `## Decisions`: the Decisions log lines that concern this wave's cards.
- `## First reading`: the repository documents this wave needs, each by its path and the part to read; only what its cards touch.

## Ledger

Sections: At a glance (sprint, `Sprint record: {name} on {board}` written at step 1 (the line the checker's SP9 and SP10 key on), `Status: {line}`, current wave, next action, last update, report, trunk verified, `Committed: {date}` written at step 12, `Released: {version} · {date} · {commit} · covers {sprints}` written by `release`, or `Release: deferred` written by `close` when it closes with no app release); **Plan steps** (one row per step, the twelve in order: `| {n} | {step} | {done date} | {evidence} |`, the step names exactly as `plan.md`'s table, empty date and evidence until done; the date as `YYYY-MM-DD`, the evidence one line with no `|`); **Waves** (from step 12, one row per wave in order: `| Wave {n} | {card ids} | {done date} | {evidence} |`; the card ids are written from the app's waves read back at step 12, `get_sprints { sprintId }`, and the debug card's own last wave has no row); Gates (one line per thing that blocks the sprint: `Gate: {blocker} delivered ({what it hands over}) before closing the sprint`, written when the link is made, the dependency gate's notice); Batch (selection rule, a table of card, title, lane, effort, complexity, order, blocked by; total effort) and Out of this sprint; Decisions log (dated, the user's decisions, the approval quoted); Waves and cards (wave, card, branch, status, last milestone, commit, review, verify, UI, merged, report section); Milestone log; Verify-first results; Conventions applied (each gap execution met that the plan's Gaps answered by convention block covered, with the block's line; never a decision of the executor's own); Plan deviations; Needs the user (backup before deploy, production audits, rule corrections awaiting approval, push and deploy decisions, unresolved references); Follow-ups noticed; Bug log. Status values: Not started, In progress (step), Paused ({reason}, awaiting the user's decision), Blocked (reason), Delivered awaiting the user's test, Tested by the user. At a glance also carries `Debug card: {short id}`, written at step 12.

The ledger is created at step 1 with every section heading above, `_Pending_` under each one not yet written, and every later write changes one section through bandit:notes (on the app's Notes `notes_update_section`, which refuses a heading the note does not have). One ledger a sprint: the wave notes copy lines from it, and nothing is written back from them.

## Wave report

One note per sprint, written for the user, rebuilt by the wave agent at the end of every wave (`execute.md` → Finishing a wave): what each card delivered, what came out different and why, the calls waiting for the user, how the work flowed and where the tokens went, all measured from the chat logs, and the lessons later plans read. Read through bandit:notes right before the rebuild, never from a local copy; each rebuilt section is written back on its own (bandit:notes edit by section), and this wave's new section, which the note does not hold yet, by one whole-text save made right after that read. Kind `reference`, the sprint's tag (in the vault `sprint` = the sprint's name), related to the ledger and the handover report.

Shape, in this order (an empty section is left out, Open calls says "None."):

- `# Sprint {name} — wave report (after wave {n})`
- `## 🙋 Open calls`: `- {card}: {the question, in app terms}. Recommend: {choice}, because {reason}. (wave {n})`. A workflow or settings lesson that reaches seen 2× is listed here too as a proposed change: Today · What changes for you · What working part it touches · Recommend.
- `## ✔️ Decided`: `- {card}: {the question} → {the user's answer, quoted}, {date}.`
- `## ⏱️ Flow trend`: `| Wave | Cards | Time | Full checks | Test runs | Gate rounds | Repeat runs | Tokens | Peak context |`, one row per wave.
- `## 📚 Lessons`: `### {short name} · seen {k}× · waves {list}`, then `- When:` (a trigger a future card can be matched on: area, kind of change) · `- Risk:` · `- Do:` (a line a plan or brief can carry; for workflow or settings, the helper rule, project rule or setting to change) · `- Use at:` (plan, brief, execution, review, workflow or settings).
- `## 🌊 Wave {n} — {date}`, then per card `### {card} {title} — ✅ As specified | ⚠️ Different | ⏸ Paused`, with only the lines that apply: `- Different: {what} — Why: {reason}` · `- Issue: {what} — Cause: {cause} — Decision: {decision} — You'll see: {impact, or "nothing"}` · `- Your call: {question}` (also in Open calls). Then `#### ⏱️ Flow` and `#### 🪙 Tokens`, pasted from `python3 ${CLAUDE_SKILL_DIR}/scripts/wave_flow.py --since {the wave's first step} --test {the project's test command}` (the script names what it counts and prints "not measured" for what the logs cannot show). The Tokens block also says where the tokens went: by source in three groups (the marketplace's plugins, Bandit Brain's connectors, everything else) with the top five items of each, an unlabelled line for steps Claude Code recorded no label on, helper agents by type, hooks by time and by the characters they add (the logs hold no tokens for hooks), and an estimated cost from the script's price list with the date it was checked, marked as an estimate, not billing. A model with no price is named, never guessed. Then `#### 🎯 Targets` (only when the project has an approved target, otherwise left out): measure, value, target, met or missed for each approved target, pasted from `python3 ${CLAUDE_SKILL_DIR}/scripts/sprint_targets.py --notes .sprint/{project}-sprint-notes.json --sprint {name} --wave {n}` run on a notes file built once this wave's Flow and Tokens are in its section (Notes file, Sprint targets).

Rules:

1. Rebuild only Open calls, Decided, Flow trend, Lessons and, once debug ends, Debug. Earlier wave sections are copied as they are, never reworded; this wave's section goes at the bottom; a rerun for the same wave replaces only its own section. An earlier section missing its Flow or Tokens block gets it, measured from that wave's logs, and its trend row completed: the only change allowed there.
2. A card delivered as specified with no issue is its heading line alone.
3. Different = anything not as its Spec and Acceptance say, a default applied by convention that changes what the user sees included. Issue = only what cost a fix, a retry, a decision or a deviation. Your call = only a choice the user could reasonably want the other way and that is still reversible, never what the Spec decided.
4. Lesson = only what can happen again on another card; a one-off bug stays an issue. Same lesson again: merge it, bump seen, add the wave. A Flow number showing avoidable time (repeat runs, a full check where a targeted test was enough, extra gate rounds) is a workflow lesson; a Tokens number showing avoidable use (a chat grown far past its start, repeated large outputs, extra UI rounds, a large start context) is a workflow or settings lesson. A missed approved target (the Targets block) is a lesson too, named `{measure} missed its target` with its waves; seen twice (two waves of the sprint) it is also an Open call as a proposed change to CLAUDE.md or a helper, and nothing is changed without the user's yes.
5. Open calls the user answered, in chat or on a card, move to Decided with their words and date.
6. Facts only, from this chat, the ledger, each card's Spec and comments, the gate verdicts, the wave's commits and the script's output. App terms, one idea per line, no preamble, no filler. Numbers never from memory; a number not measured is written "not measured", never estimated.
7. Touch nothing else while writing it: no code, ledger, cards or other notes.

## Pre-sprint estimate

Each wave's time estimate is a forecast written into the plan's Summary wave table at plan step 12, and the sprint's total into the first line of step 12's report. `python3 ${CLAUDE_SKILL_DIR}/scripts/sprint_data.py --estimate {data.csv} --effort {each wave's effort, in wave order}` reads the project's sprint data file (Sprint data, below) and gives minutes per effort point: the median over the past waves that have both a time and an effort, the middle half as the range, and how many waves it used. Fewer than 5 past waves: no figures, and the table and the report say "no estimate yet". The estimate is labelled as one; it never goes into the ledger or the wave report's measured numbers. (The sprint map page this helper drew until the app's 0.56.0 is retired: the app's sprint page draws the map.)

## Sprint data

One data file per project, built by `python3 ${CLAUDE_SKILL_DIR}/scripts/sprint_data.py --notes .sprint/{project}-sprint-notes.json` from the project's sprints, live and archived, on a fresh notes file (Notes file): one CSV row per wave (`sprint`, `where`, `wave`, then one column per measure). Numbers come only from the ledger and the wave report; a measure a record does not hold is an empty cell, never an estimate, and a ledger with no wave table is skipped with a note. **The measures list is the one place a measure lives**: one `Measure(name, source, reader)` line in the script's `MEASURES`, and a new measure is a new column with nothing else changed (`sprint_data.py --list` prints the names and where each is read). A project's targets are not in the script: they live in the targets note (Papers), so they change without a release.

Write the CSV to its home (Papers → Files that are not text): on the app's Notes `.sprint/{project}-sprint-data.csv` at the root of the repository the helper runs from; in the vault `Projects/{slug}/planning/{project}-sprint-data.csv` through WebDAV, a new file the first time, then the etag, bare, on each rebuild (bandit:notes write rules). `execute.md` → Finishing a wave runs it after the wave report, and `close.md` runs it before the archive; a rebuild replaces the whole file.

## Sprint targets

A project's targets live in its targets note (Papers), one table keyed by measure name: `| Measure | Target | Direction | Status | Approved | Words |`, direction `at most` or `at least`, status `proposed` or `approved`. **A target is used only once approved**: status `approved` with the approval date and the user's own words written in the row; a proposed row, or an approved one missing its date or words, is never shown as met or missed. Only a measure whose line in the script's measures list names a direction can carry a target (a new measure takes one with `direction=` on its line). The first targets are proposed, not set: `sprint_targets.py ... --propose` prints a `proposed` row for each measure without one, taken from the median of the project's data rows; they are written to the note as `proposed`, and the user's yes turns a row to `approved` (never before). `sprint_targets.py ... --sprint {name} --wave {n}` prints the wave report's Targets block and the Lessons lines of its misses; without `--wave` it prints the sprint table for the closing report (waves met, waves missed, result) in the handover report's Targets section. A value the records do not hold reads "not measured", never met or missed.

## Debug card

One card per sprint, the single shared list of what to fix in debug, assigned to the user, in the sprint alone in its last wave (plan step 12), so the waves of work finish without it. Title `Debug: sprint {name}`. Description: one `<p>` saying "One line per issue. Claude adds what a wave could not solve; add what you find, or tell Claude and it adds it." and the three line shapes below. In any card description a `<pre>` is never the last block: the app shows a description that ends in `</pre>` as raw tags, and the description gate refuses the write.

- **Line shapes** (checklist lines, one idea each, no codes, details in a comment): `Expected: {screen} › {part} — {what is wrong, in app terms} ({card})` for one Claude raises; `Found: {screen} › {part} — {what is wrong} ({card})` for one the user finds. `{screen} › {part}` is the area as the user sees it; `{card}` is the sprint card it belongs to, or `new`. `Process: {step} — {what went wrong} ({card or sprint})` for a build, check, push, gate, board move, release step or run that stalls or fails: `{step}` names it in plain words, `{card or sprint}` is the card it hit, or `sprint`.
- **Process lines** (the one home of this rule): the wave, `run`, `debug` or `release` step that meets a stalled or failed step writes one Process line at once, when it happens, one line per stalled step (a retry of the same step adds none), and says so in its report. Not for a defect in what a card delivered: that is `Expected:` or `Found:`. The line is what lets the closing report and the lessons stop the same problem coming back.
- **Moves.** The card follows the work on the Execution board: `assigned` from planning; `doing` when `debug` starts (`debug.md` → Intake); `standby` when `release` starts (`release.md` → Steps); completed by `close`. A wave and `run` never move it. In `doing` it takes one place of the five across Next and Doing.
- **Outcomes:** a Process line is ticked once it is fixed or its lesson is recorded in the wave report's Lessons; a fixed line is ticked; a declined one ends `(declined: {reason})` and is ticked; one that is new work ends `(new card {id})` and is ticked.
- **Wave report, Debug section** (written when debug ends, after Lessons; rebuilt like Open calls and Lessons, rule 1; SP11 does not read it): `## 🐞 Debug`, then `| Card | Expected | Found | Process | Fixed | Declined | New card |`, one row per card (a Process line on the whole sprint counts on a `sprint` row) and a total row, counted from the card's lines. Every Process line is read for the Lessons: its step is the `When:`, what went wrong the `Risk:`; one still unticked is named in the closing report. A card kind that keeps producing Found lines is a lesson.

## Approval line

The one home of this rule. Every batch card of a sprint planned with this rule ends with one sub-task titled exactly `Tested and approved by you`, **last**, after the build steps and any `Gate:` lines, open. It shows that a card whose build steps are all ticked still waits for the user. The user ticks it once they have tested the card: a ticked line is their approval, and `close` then runs without asking (`close.md` → Preconditions). Of the helpers, only `close` ticks it, and only for a card the user approved in that chat, with the approval quoted in the ledger (`close.md` → Steps); a wave, `run` and `debug` never do. `close` completes no card whose approval line is open. Not a tag, not a feature of the app: the app lets a card be completed with open sub-tasks, so the helpers hold the line. The debug card has none. A card from a sprint planned before this rule has no such line and closes as before.
