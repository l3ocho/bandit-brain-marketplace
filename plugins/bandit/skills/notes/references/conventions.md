### 1. Folders

#### Core — every domain has all of them

| Folder | Purpose | Rule |
|---|---|---|
| `README.md` | Home page + domain config | Generated by `/bandit:notes home`. Its frontmatter is domain config, **exempt** from the note frontmatter in §5 |
| `_inbox/` | The user's working space. Obsidian's "new note location" points here | Every new note lands here first. **No conventions apply and nothing is edited here** until the user reviews it (`references/model.md`, *The inbox is the user's*) |
| `_templates/` | Input structures (new note, meeting entry, request) | Pre-filled standard keys (§10) |
| `_archive/` | Done notes | Mirrors the original path (§7) |
| `_attachments/` | Every non-markdown file a note embeds. Obsidian's "attachment folder path" points here | Flat, never mirrored; stays put when notes move (§8) |
| `Claude/` | Claude settings only | See §3 |
| `Projects/{slug}/` | One folder per project | Holds the **hub note** `{slug}.md` (below). Everything else inside is up to the project's own settings |

#### Project hub note

`Projects/{slug}/{slug}.md` is the project's one fixed file: `type: reference`, a `summary` of the
project, and links to its main docs. It exists so the project is a **link target** — every note
about the project sets `project: "[[{slug}]]"`, and the hub's backlinks pane then lists all of
them (meetings, requests, briefs) without this skill ever editing the hub. The skill creates the
hub once (on approval) and afterwards treats it as an ordinary note the user owns.

#### Sprint folders

`Projects/{slug}/sprint-{name}/` holds one sprint's records on a dev project (§13). `{name}` is the
sprint's name, the same word as its `sprint/{name}` tag on the board (`sprint/debut` →
`sprint-debut/`). Nothing else goes in it.

| Record | Filename | `type` | `board-task` |
|---|---|---|---|
| Plan (the one shared technical plan) | `{project}-sprint-{name}-plan.md` | `plan` | the sprint card |
| Execution prompt (instructions for the execution chat) | `{project}-sprint-{name}-handover-prompt.md` | `reference` | the sprint card |
| Ledger (live progress) | `{project}-sprint-{name}-progress.md` | `reference` | the sprint card |
| Report (handover test report) | `{project}-sprint-{name}-handover-report.md` | `reference` | the sprint card |
| Review (the independent plan review, sprint plan step 11) | `{project}-review-sprint-{name}-YYYY-MM-DD.md` | `log` | the sprint card |
| Briefs of the sprint's cards | §4 brief pattern | `brief` | that card |

**Written straight in**, like the planning documents (`references/other-skills.md`): these records are
worked on across many sessions while the sprint runs. They still follow §5 (frontmatter, `status`,
YAML style), create fail-closed and edit only with the etag. A brief that already sits in the
project folder or the inbox moves into the sprint folder when its card joins the sprint (`file`).

**Sprint project root.** Once a project has a sprint folder, the root of `Projects/{slug}/` holds
only the hub note `{slug}.md`, the `sprint-*` folders and `planning/`. The WBS (`{slug}-wbs.md`),
the project plan and the architecture live in `planning/`, and so does every other note about the
project that isn't a sprint's record (a brief or plan note whose card is in no sprint yet, for
instance). It moves into the sprint folder when its card joins one. `file` and `file-to` use
`planning/` as the project destination on such a project.

**Archiving a sprint.** At close, the plan, execution prompt, ledger, review record and report take `status:
done`; then the whole folder moves in one proposal: `Projects/{slug}/sprint-{name}/` →
`_archive/Projects/{slug}/sprint-{name}/`, every note stamped (§7), the missing mirror folders
listed as rows.

#### Root level of `MyNotes`

| Pattern | Meaning |
|---|---|
| `_name/` | Not a domain. Never scanned, scaffolded or linked |
| `.name/` (e.g. `.templates/`) | Ignored |
| anything else | A domain |

Skills are not vault content: their single source is the bandit-brain-marketplace repo. This
skill never scans, lints or writes anything in a root `_` folder.

### 2. Modules

Optional folders, switched on per domain in the README `modules:` list. The folder name is fixed
and generic on purpose: it says what's inside, in every domain.

| Module key | Folder | Holds | Dated? |
|---|---|---|---|
| `meetings` | `Meetings/` | Every meeting's minutes or entry note, **including project meetings** | Yes |
| `requests` | `Requests/` | Outstanding asks from other people: analyses and one-off work outside the daily routine | Yes |

- **Project meetings live in `Meetings/`**, with `meeting: project` and `project: "[[{slug}]]"`.
  The project reaches them through the README's per-project meeting list and through the hub
  note's backlinks — the minutes link the project, not the other way round, so this skill never
  has to edit a note inside a project folder.
- A folder that fits no core folder and no module is never an invitation to invent one. `onboard`
  and `lint` return it as a fix row with the options, recommended first: map it to an existing
  module, move it under `Projects/`, or propose a new module (which means changing this file).

### 3. The `Claude/` folder — settings only

```
Claude/
├── ai-{slug}/       ← a Claude.ai project's settings (managed by bandit:project)
├── code-{slug}/     ← a project's Claude Code settings: the Claude Code twin (CLAUDE.md, claude/settings.json, claude/hooks/workdir.py) of a project without dev: true, or a dev repo's mirror (CLAUDE.md + claude/)
└── design-{slug}/   ← a Claude Design project's settings
```

- Prefixes mirror the bandit:tasks Handler tags: `claude-ai` → `ai-`, `claude-code` → `code-`,
  `claude-design` → `design-`.
- `{slug}` is the project's name in lowercase kebab-case: "Acme Workflow" →
  `ai-acme-workflow`; the Home Reno repo → `code-home-reno`.
- **Only settings go here** — the instructions file and the reference doc it points to, CLAUDE.md
  copies, configuration, and nothing else. **Explicitly excluded** (these are NOT settings): project
  logs, working notes, decision journals, discussion/chat records, reports, briefs, plans and drafts.
  They go to `Projects/{slug}/` (project work) or the domain's other folders, never into `Claude/`.
- **No skills.** Skill sources live in the bandit-brain-marketplace repo, never in the vault.
- Files in `ai-*` are written by bandit:project as `{prefix}-{type}-v{N}.md` and start with an
  HTML metadata comment on line 1. They're exempt from frontmatter and from the filename rules
  below. Never add YAML to them.

### 4. Filenames

Lowercase kebab-case, `.md`, no spaces, no dates in the middle.

| Kind of note | Pattern | Example |
|---|---|---|
| **Dated** (something that happened or arrived on a day) | `{slug}-YYYY-MM-DD.md` | `department-minutes-2026-09-23.md` |
| **Evergreen** (reference, living document) | `{slug}.md` | `genesys-queue-map.md` |
| **Project hub** | `Projects/{slug}/{slug}.md` | `Projects/home-reno/home-reno.md` |
| **Attachment** | `{note-slug}-{what}.{ext}`, in `_attachments/` | `department-minutes-2026-09-17-seating.png` |
| **Brief** | `{project}-{lane}-{slug}-YYYY-MM-DD.md` | `home-reno-feature-export-button-2026-09-23.md` |
| **Plan** (dev projects, §13) | `{project}-{lane}-{slug}-plan.md`, `{lane}` the bare value (`feature`, not `lane/feature`) | `home-reno-feature-export-button-plan.md` |
| **Sprint records** (dev projects, §1 Sprint folders) | `{project}-sprint-{name}-{record}.md`, `{record}` = `plan` · `handover-prompt` · `progress` · `handover-report`; the review record is dated: `{project}-review-sprint-{name}-YYYY-MM-DD.md` | `home-reno-sprint-debut-plan.md` |
| **Settings** (`Claude/ai-*`) | `{prefix}-{type}-v{N}.md` | `sw-instructions-v1.md` |

Dated by type: `minutes`, `request`, `brief`, `log`. Evergreen: `note`, `reference`, `plan`.

**Cards point to notes by filename, never by path.** The name survives the `_inbox/` →
`Projects/` move, and uniqueness (below) guarantees one match.

**Minutes slugs** encode the meeting, so the README can group them without opening each file:
`{meeting}-minutes-YYYY-MM-DD.md` (`supervisors-minutes-…`, `department-minutes-…`), and for
project meetings `{project}-minutes-YYYY-MM-DD.md` (`home-reno-minutes-…`). The short version of
minutes adds `-short` before the date.

**Uniqueness is mandatory.** Obsidian resolves `[[name]]` by filename, and WebDAV moves don't
update links, so two notes with the same name break links silently. Before creating, filing or
renaming, check with `nc_webdav_find_by_name(pattern="{filename}", scope="MyNotes/{Domain}")`.
On a collision, make the slug more specific (`department-minutes-pm-2026-09-23`,
`genesys-queue-map-billing`). Never add `-2` style counters. **Exempt:** `README.md`, the
domain's generated home page; nothing links to it by name.

Kebab-case also keeps out the characters Obsidian reserves in links: `# | ^ : [ ] %`.

Inbox notes keep whatever name the user or Obsidian gave them ("Untitled 3.md", "Meeting - Project
Updates.md") until review renames them on the way out.

### 5. Frontmatter

YAML, **kebab-case keys** (matching the existing templates). Values in ISO dates. The skill adds
missing keys and fixes malformed values; it **never removes a key or a tag the user added**.

Exempt: notes in `_inbox/` (until reviewed), the domain `README.md` (its frontmatter is domain
config) and the `Claude/ai-*` settings files (line-1 HTML metadata, §3), including archived
ones in `_archive/Claude/ai-*`.

#### Every note

| Key | Values | Notes |
|---|---|---|
| `type` | `note` · `minutes` · `request` · `brief` · `reference` · `log` · `plan` | What the note is (`plan`: dev projects only, §13) |
| `status` | `inbox` · `triaged` · `active` · `waiting` · `done` | See §6 |
| `domain` | Domain folder name, e.g. `Acme` | |
| `summary` | One sentence, ≤ 25 words | What the note covers, written so an agent can decide from the frontmatter alone whether to open it. Not needed in the inbox; **required once reviewed**. The README lists it next to the link |
| `created` | `YYYY-MM-DD` | Replaces the legacy `created-date` |
| `updated` | `YYYY-MM-DD` | Date of the last edit **made through this skill or another skill**. The user's hand edits in Obsidian don't bump it; the WebDAV modified time is the true last-touched date |
| `tags` | list | The user's own. Untouched |

#### When they apply

| Key | Values | Used by |
|---|---|---|
| `project` | `"[[{slug}]]"` — a link to the project hub note | any note about a project. A bare slug (v1 form) is flagged by `lint` and migrated by `onboard`. **Before onboarding** (no hub yet): leave `project` out and set `file-to: Projects/{tentative-slug}/`; `file` adds the key once the hub exists (Part 3, `file`) |
| `aliases` | list of other names | optional; helps search and link suggestions. Never a substitute for fixing links after a rename (`references/write-safety.md`) |
| `source` | `chat` · `manual` · `meeting` · `email` · `migrated` | where the content came from. `migrated` = moved in from another system (a repo, a wiki, the Notes app, an older vault layout) by whichever step moves it; the original location goes in the body's first line |
| `board-task` | Bandit Brain task id | link to the task that tracks the work |
| `related` | list of `"[[wikilinks]]"` | links inside the same domain |
| `file-to` | folder path inside the domain, e.g. `Meetings/` | filing hint for `/bandit:notes file` |
| `kind` | `feature` · `issue` · `chore` | bandit:tasks Kind vocabulary (briefs). **Not written on dev projects**: `lane` carries it. An existing `kind` stays (never remove a key the user added) |
| `handler` | `claude-code` · `claude-design` · `claude-ai` | bandit:tasks Handler vocabulary |

#### By type

| Type | Extra keys |
|---|---|
| `minutes` | `meeting`: `supervisors` · `department` · `project` (nothing else) — `meeting-date`: `YYYY-MM-DD` — `participants`: list of names mentioned — `room`: where it was held (free text, optional) |
| `request` | `requester`: a **role**, not a name ("CS Director", "Billing team") — `received`: date — `due`: date or empty |
| `brief` | `lane`: the repo's lane name (on a dev project, the bare lane value: `feature`) — plus `kind` (not on dev projects), `handler` |
| `plan` | `lane`: the bare lane value; **left out on a sprint plan** (a sprint has no lane) — `board-task`: **required**, the card's task id, or the sprint card's on a sprint plan — `related` |
| archived notes | `archived-from`: original folder path — `archived`: `YYYY-MM-DD` |

`meeting` has **exactly three values**, the ones in the Source picker of the user's meeting template:
`supervisors`, `department`, `project`. That picker is the standard and the user has settled it:
there is **no Ad-hoc and no Outstanding**. Never propose, add or suggest another value or picker
option ("ad-hoc", "other", "misc"…), and never edit the picker. "Outstanding" is the `Requests/`
module, not a meeting. If a meeting fits none of the three, ask the user which one it is; don't invent one.

#### YAML style — write it the way Obsidian writes it

Obsidian's Properties editor rewrites the YAML whenever the user touches a property. Writing in its
style means their edits don't reformat the file (noisy diffs, fresh etags on every touch).

- **Lists in block style**, one `- item` per line, even for one item. Never `[a, b]`.
- **Links quoted:** `- "[[note-name]]"`, `project: "[[home-reno]]"`. Unquoted `[[…]]` is invalid YAML.
- **Dates unquoted** `YYYY-MM-DD`. **Empty values** as `key:` with nothing after it.
- **No `#`** in `tags` values.
- **Quote a value YAML would misread.** Any scalar that contains `: ` or ` #`, or starts with a
  quote, `[`, `{`, `&`, `*`, `!`, `|`, `>`, `%`, `@` or a backtick, goes in double quotes (inner
  `"` escaped as `\"`). `summary` is the usual offender. Unquoted, the note opens in Obsidian with
  invalid properties.
- **Key order** (keys that don't apply are skipped, unknown keys the user added go last, untouched):
  `type · status · domain · project · summary · created · updated · {type-specific keys} ·
  source · board-task · related · file-to · kind · handler · aliases · tags`
  Archive stamps (`archived-from`, `archived`) go right after `updated`.

#### Property types

Obsidian keeps **one type per property name for the whole vault** (`.obsidian/types.json`). A
key typed inconsistently breaks sorting, filters and Bases views. Target types:

| Type | Keys |
|---|---|
| Date | `created` · `updated` · `meeting-date` · `received` · `due` · `archived` |
| List | `tags` · `aliases` · `related` · `participants` |
| Text | everything else (`project` stays Text: a quoted link is still text) |

Set once per vault — in the app (Properties view → change type) or with `/bandit:notes settings`.
`lint` checks them (§11).

#### Querying these keys (Bases, Dataview)

Hyphenated keys (`board-task`, `meeting-date`, `file-to`) parse as subtraction in Bases and
Dataview formulas. Reference them with bracket syntax (`note["board-task"]`). A live view is an
Obsidian convenience only: an agent reading over WebDAV can't run it, so the README's static
tables stay the source an agent reads.

### 6. Status

A note's lifecycle, **independent of the task board**. The board owns work state
(`backlog · assigned · next · doing · standby · done`); the note links to its task through
`board-task` and never mirrors that state — two copies of one state drift the first time a task
is ticked on the phone.

| Status | Means | Where it lives |
|---|---|---|
| `inbox` (or none) | The user's, in progress. No rules, not edited | `_inbox/` only |
| `triaged` + `file-to` | Written by a skill, waiting for the user's review | `_inbox/`. `file-to` is removed at review |
| `triaged` | Filed and structured; nothing pending on it | its home folder |
| `active` | Being worked on or referenced as current | its home folder |
| `waiting` | Blocked on someone else | its home folder |
| `done` | Finished — **ready to be archived** | `_archive/` after `/bandit:notes archive` |

There is no `archived` status: `done` plus living in `_archive/` is the signal. A `done` note
outside `_archive/` is a pending archive, which `lint` and the README both surface.

**The one exception: plan notes (§13).** A `plan` note's `status` tracks its card's **existence
and completion** only: `active` while the card is open, `done` once it's complete. The card's stage
(`stage/*`) and execution state are never copied. Every other note keeps "independent of the board".

### 7. Archive

- **Mirror the path:** `Projects/home-reno/x.md` → `_archive/Projects/home-reno/x.md`.
  `Meetings/y.md` → `_archive/Meetings/y.md`. Restoring is the reverse move.
- **Stamp before moving:** set `archived-from: Projects/home-reno/` and `archived: YYYY-MM-DD`,
  then move. The stamp is the backup if the mirrored path is ever disturbed by hand.
- The filename doesn't change, so links keep resolving.
- Missing mirror folders under `_archive/` are part of the approved archive proposal — list them.
- **A whole sprint folder** archives as one proposal: every note in it stamped, then the folder
  moved to `_archive/Projects/{slug}/sprint-{name}/` (§1 → Archiving a sprint).
- **Settings versions** (`Claude/ai-{slug}/`) mirror the same way,
  `_archive/Claude/ai-{slug}/`, but are **moved only, never stamped**: they carry no frontmatter.

### 8. Non-markdown files

Obsidian syncs everything: images, PDFs, audio, `.canvas`, `.excalidraw`, `.base`.

- **Never edit them.** A bad write to a `.canvas` or `.excalidraw` file corrupts it.
- **Attachments live in `_attachments/`** and **don't move when their note moves**: embeds
  resolve by filename, so `![[file.png]]` keeps working from any folder. Archiving a note leaves
  its attachments where they are.
- **Attachment names** follow §4 (`{note-slug}-{what}.{ext}`). Obsidian names pasted images
  `Pasted image 2026….png`; `file` and `lint` propose the rename together with the embed update
  in the note (a rename breaks the embed otherwise).
- **Attachments found elsewhere** (next to a note, from before v2) are a `lint` fix row: move
  them to `_attachments/`, with the embed updates.
- **A standalone file in `_inbox`** (a PDF dropped from the phone) gets a **sidecar note**: a
  `.md` with the same slug, the standard frontmatter and an embed (`![[file.pdf]]`). Filing
  moves the file to `_attachments/` and the sidecar to its home; the sidecar carries the
  metadata.
- `.canvas` and `.base` files are Obsidian documents in their own right: they may live in any
  content folder, and they're filed by name only.

### 9. Ignore list

Never scanned, moved or reported as out of place:

- `.obsidian/`, `.trash/`, and any other dot folder or dot file — with one exception: the
  `.obsidian/` settings files on the §11 allowlist, which `lint` reads and `/bandit:notes settings`
  reads and writes
- Root `_` folders of `MyNotes`

**Flagged, never touched on their own:** sync-conflict copies (`* (conflicted copy)*`,
`*.sync-conflict-*`, `* (1).md` duplicates next to an original). Report them in `lint` and on
the README. Once the user says which copy wins, the loser can go in a `delete` row.

### 10. Templates

Templates in `_templates/` carry the standard keys, **pre-filled wherever the value is known
when the note is created**, so every note Obsidian makes from them starts compliant. Keep the user's
structure (headings, pickers) exactly as they wrote it. Only the frontmatter is standardised.

| Key | In the template |
|---|---|
| `type` | Fixed when the template implies it (`minutes`, `request`); empty in `new-note.md` |
| `status` | `inbox` |
| `domain` | The domain name, written in |
| `created`, `updated` | `{{date:YYYY-MM-DD}}` — filled by Obsidian's core Templates plugin on insert |
| `summary` | Empty (filled at filing) |
| everything else | Empty |

- The `{{date:…}}` syntax is the **core Templates plugin**. If the vault uses the Templater
  community plugin instead (`.obsidian/community-plugins.json` lists `templater-obsidian`), the
  equivalent is `<% tp.date.now("YYYY-MM-DD") %>`. `lint` checks which one the vault runs.
- Standard set per domain: `new-note.md` always; a meeting template when `meetings` is on; a
  `request.md` when `requests` is on (keys: the standard ones plus `requester`, `received`, `due`).
  The user may name the meeting template as they like; it's identified by `type: minutes`.
- A picker in a template body is the user's input device. When it duplicates a frontmatter key
  (e.g. the meeting Source picker vs. `meeting:`), the **frontmatter value is the one agents and
  the README read**; `file` copies the picked value into the key in lowercase.

Legacy key map, applied by `onboard` and `lint`:

| Legacy | Standard |
|---|---|
| `created-date` | `created` |
| `subject` | the title (`# …`) + slug; the key may stay |
| tag `doc-minutes` | `type: minutes` (the tag stays) |
| `project: {slug}` (v1) | `project: "[[{slug}]]"` |

### 11. Obsidian settings (per domain vault)

This skill's rules assume these settings. `lint` reads them; **`/bandit:notes settings` is the only
command that writes them**, on approval, under the safety rules below. A key missing from the
JSON means Obsidian's default is in effect.

| Setting (Obsidian UI) | File · key | Required value (JSON) | Default | Why |
|---|---|---|---|---|
| Files & links → Default location for new notes | `app.json` · `newFileLocation` / `newFileFolderPath` | `"folder"` / `"_inbox"` | vault root | Every note lands in `_inbox` |
| Files & links → New link format | `app.json` · `newLinkFormat` | `"shortest"` | `shortest` ✓ | Path-free links survive WebDAV moves |
| Files & links → Use [[Wikilinks]] | `app.json` · `useMarkdownLinks` | `false` | `false` ✓ | Filename-resolved links |
| Files & links → Automatically update internal links | `app.json` · `alwaysUpdateLinks` | `true` | off | In-app renames rewrite backlinks |
| Files & links → Default location for new attachments | `app.json` · `attachmentFolderPath` | `"_attachments"` | vault root | §8 |
| Files & links → Excluded files | `app.json` · `userIgnoreFilters` | array containing `"_templates/"` (other entries kept) | none | Keeps empty-template frontmatter out of search, graph and link suggestions |
| Templates → Template folder location | `templates.json` · `folder` | `"_templates"` | unset | Insert-template can find them |
| Templates → Date format | `templates.json` · `dateFormat` | `"YYYY-MM-DD"` (or unset + explicit `{{date:YYYY-MM-DD}}`) | `YYYY-MM-DD` | ISO dates |
| Core plugins → Daily notes | `core-plugins.json` · `daily-notes` | `false`, **or** `daily-notes.json` · `folder` = `"_inbox"` | on, vault root | A date-only file at the root breaks §4 |
| Core plugins → Sync | `core-plugins.json` · `sync` | `false` when BanditCloud syncs the vault — **only after the user confirms they don't use Obsidian Sync on this vault** | on | Two sync engines on one folder produce conflict copies |
| Properties → types | `types.json` · `types.{key}` | `"date"` for §5 Date keys · `"multitext"` for `related`, `participants` | inferred | Consistent types. `tags` and `aliases` keep Obsidian's own `"tags"` / `"aliases"` types — never change them |

Key names are as of Obsidian 1.9. If a setting is missing from a file, report "not set (default
applies)", not a breach, unless the default is wrong.

#### Writing `.obsidian/` safely

Obsidian keeps its settings in memory while a vault is open and writes them back on its own
schedule, and the files sync to every device through BanditCloud. A write that ignores either
fact gets silently undone, or spreads a broken file everywhere. So:

- **Allowlist.** Only these files: `app.json`, `templates.json`, `core-plugins.json`,
  `daily-notes.json`, `types.json`. Only the keys in the table above. Never `workspace*.json`,
  `community-plugins.json`, `hotkeys.json`, `appearance.json`, `graph.json`, or anything in
  `plugins/`, `themes/` or `snippets/` — those are read at most, never written.
- **Obsidian closed everywhere.** Before executing, the user confirms that Obsidian is closed on
  **every** device that opens this vault (desktop and phone). No confirmation → no write.
  Never in a scheduled or unattended run.
- **Backup first.** Before the first edit to a file in a run, copy it with
  `nc_webdav_copy_resource` (`overwrite: false`) to
  `.obsidian/mynotes-backup/{file}.{YYYY-MM-DD-HHMM}.json`. Create `mynotes-backup/` first with
  `nc_webdav_create_directory` if it's missing (a 409 on the copy means it is). Obsidian ignores
  unknown folders there. If the backup fails, skip that file's rows.
- **Merge, never replace.** Read the file, parse the JSON, change only the approved keys, keep
  every other key and its value exactly. Write with 2-space indentation. A file that doesn't
  exist yet (e.g. `templates.json`) is created with only the approved keys.
- **Validate before and after.** The new text must parse as JSON before it's written; if the
  current file doesn't parse, stop and report — never "fix" a file you can't read. After the
  write, re-read, parse, and confirm each approved key has its new value.
- **Etag.** Existing files: read → bare-hex etag → `if_match`, as for notes. JSON files may come
  back with a `-gzip` suffix on the etag (`c486…dc0f8-gzip`): strip it too. A 412 means
  something changed the file since the read (Obsidian still open, or a sync) — or the etag
  format wasn't accepted: stop, report, don't retry, never fall back to `if_match: "*"`.
- **After the run**, tell the user: wait for BanditCloud to finish syncing, open Obsidian on the
  desktop first, check the changed settings in the UI, then open other devices. Obsidian may
  add its own default keys to the file on first open — that's normal.

### 12. Note body shape (notes a skill or chat writes)

The user's own notes and templates keep their structure. Notes written by a skill or in a chat
(briefs, drafts, references, logs) use this shape, so any agent can take the slice it needs
without reading the whole file:

1. **One H1**, the note's title, matching the filename's meaning.
2. **Summary line** directly under it: `> {same sentence as the summary key}`.
3. **H2 sections**, short, H3 inside when needed. Tables over paragraphs for structured facts.
4. **Unambiguous dates** in the body: `YYYY-MM-DD` or a written month ("Sep 21"). Never
   `09/10/2026`.
5. **`## Related`** last, when the note links anything: one line per link with the reason —
   `- [[home-reno]] — project hub` · `- [[department-minutes-2026-09-17]] — decision source`.
   Every link here also appears in `related` (or `project`) in the frontmatter.
6. **No customer data** (names, account numbers, addresses, call contents). Use placeholders
   (`[customer]`, `[account]`).

Minutes follow the bandit:minutes skill's layout, which already meets 1 and 3; they add the
summary line (2), `## Related` (5) when they link other notes, and rule 6 applies to them in full.

### 13. Dev projects (`dev: true`)

Written only from a project whose Project Context has `dev: true` (key owned by bandit:project).
Every other project keeps the rules above unchanged. Once written, a `plan` note carries its own
rules wherever `file` or `lint` meet it. The card workflow itself is bandit:tasks'
(`references/dev-workflow.md` there).

- **Plan notes** (`type: plan`, §4 filename, §5 keys, §6 status exception) hold a card's full
  technical plan: the plan itself and the landing/commit sequence for an L card (any WBS L4 lines:
  bandit-dev:sprint's rule). Body per §12. They're written **inbox-first** like any skill-written note
  (`status: triaged`, `file-to: Projects/{slug}/`, or its `planning/` on a project with sprint
  folders, §1); they are **not** part of the planning-docs exception.
  **Sprint plan:** one plan note shared by every card of a sprint, written straight into the sprint
  folder (§1), no `lane`, `board-task` = the sprint card. Each card's `Technical plan` names its
  filename.
- **Card briefs** (`type: brief`, §4 filename, §5 keys) are the long form of one card's Spec: one
  brief per card, `board-task` = the card's short id, written when `/bandit:tasks spec` writes the
  card (the card names it by filename). **Inbox-first** like any skill-written note (`status:
  triaged`, `file-to: Projects/{slug}/`, or its `planning/` on a project with sprint folders, §1). Body per §12, with these H2s in order: `## Summary` ·
  `## Scope` (**In scope** / **Out of scope** lists) · `## Requirements` (table: `#` · Requirement ·
  Priority `Must`/`Should`/`Could` · Notes) · `## Decisions` (dated) · `## Verified facts
  (YYYY-MM-DD)` (each with where it was checked: a file, a tool result) · `## Open questions` ·
  `## Change log` (optional: one dated line per change to the brief and why) · `## Related`.
  **No card state in the body** (column, lane, stage): the card holds it, so a copy goes stale. A
  `Card: {short id}` line under the summary is fine; the short id never changes. A sprint card's
  briefs live in its sprint folder (§1).
- **WBS card links.** `{slug}-wbs.md` (in `Projects/{slug}/`, or its `planning/` on a project with
  sprint folders, §1) carries a `## 🔗 Card links` table (format owned by bandit:plan: WBS id ·
  card id · card title at creation · created). A row is added when its card is created, or, for a
  card that already exists, when bandit:plan builds a WBS over it (sprint mode). Writer: the chat
  that ran `/bandit:tasks spec` or bandit:plan, through this skill, as an edit of an existing
  note: its own approval row, etag-guarded write, `updated` bumped.
- **WBS levels:** the names are bandit:plan's; L3 = one card is bandit:tasks'
  (`references/dev-workflow.md`); where L4 lines go is bandit-dev:sprint's.
