# 🏁 The close cycle

Part of `bandit-dev:sprint`. Read before running `/bandit-dev:sprint close {sprint}`. Run only after debug and release are done. Archive rules are owned by bandit:notes (on the app's Notes status `archived`, `references/storage-app.md` → Archive, restore, delete; in the vault `references/conventions-vault.md` §7); completion rules by bandit:tasks. Where a sprint's papers are: `references/templates.md` → Papers.

Contents: Preconditions · Steps · Never

## Preconditions

Check all, report any miss as a fix row, and stop:

1. Ledger "At a glance" says debug is done and no row is open (or debug never ran and the user says so: record that).
2. **The debug card** (`Debug card:` in the ledger), when there is one, has every line ticked; an unticked line refuses the close and is named. Every batch card is in `standby`, or already complete (the user may have completed some by hand: that is fine, close is idempotent). None has an open sub-task, except an open approval line (precondition 3). Any other open sub-task: name it.
3. **The user's approval.** A batch card whose approval line the user has ticked is approved: they tick it once they have tested it (`references/templates.md` → Approval line), and running `close` is then the go for every step below, the archive included, with no question. Record it in the ledger as `Approval line ticked by the user` with the date read. Only a card whose approval line is open needs the user's approval, or their statement that they tested it, in this chat, in their own words: ask once, naming those cards only, and quote the answer in the ledger. A card left open stays open and is never completed. The user stops or changes the close by saying so.
4. **Release, the user's option.** The ledger has a `Released:` line (written by `release`), or the sprint closes with no app release: then write `Release: deferred` in At a glance (the next release covers it, `release.md` → Covering), add one Milestone log line saying the same, and say so in the report. **A sprint that changed the helpers** (Marketplace cards) still needs the plugin release before it closes: no plugin version in a `Released:` line → refuse and give the paste for `release`.
5. **Close makes no commit.** A released sprint: after `git fetch`, `git rev-list --count origin/{branches.deploy}..origin/{branches.trunk}` and the same for the local trunk print `0`. Anything else is refused, naming the commits (`git log --oneline`): they go to a new release or a card for a later sprint, never into this close. A sprint with `Release: deferred` skips this check.
6. Nothing needs the user that blocks closing. The ledger's needs-the-user list is read to them once; items for deploy, or a push that failed, stay open and go to the report (step 5), they do not block.

## Steps

Read the live state first (`get_sprints { sprintId }`, `get_task` for every card, the ledger, the report). **Every step checks before it writes: a state already correct is left alone and reported as "already done".**

0. **Cards that do not close (detached, carried, or not approved in this chat), first:** the app refuses to close a sprint holding an open card, and a Closed sprint takes no change. For every batch card that stays open (one detached to the next sprint, or one that waits for a trigger): take it out of the sprint (`manage_sprints { action: "remove_card" }`), leave it in Backlog, and write "detached" on its ledger row. **Then merge everything the sprint knows about it into its brief, before the archive**: what the plan, ledger and report say about the card (state, remaining steps, findings, decisions, acceptance-to-proof) in a closing section of the brief, which keeps its title so the card's `Brief:` line still resolves. One document per card, and it leaves this sprint's papers so the archive does not take it: on the app's Notes it stays linked to its card and loses this sprint's tag (the next `plan` gives it that sprint's tag); in the vault it moves, not copied, into the inbox (`status: inbox`, `file-to:`), and the next `plan` files it into the next sprint folder. The checker enforces it in the vault (SP2 skips a detached card, SP6 fails a second brief for the same card).
1. **Tick the approval line, then complete the cards.** First, for each card the user approved in this chat (precondition 3), with the approval quoted in the ledger, `manage_subtasks { action: "tick", subtaskId, completed: true }` on its approval line, then read the card back: a card whose approval line is open is not completed and goes to step 0. A card from a sprint planned before the approval line existed has none and closes as before. Next, on a project whose notes are in the app's Notes (`notes: app`; a vault project skips this and closes as before), **each batch card's conclusions go into its linked note** (bandit:notes `references/conclusions.md`), unattended: running `close` is the go for those note writes, the cards' descriptions are left as they are, and a card with no linked note, two of them, or one still in the Inbox gets nothing written and is named in the report (step 5); a refused write is reported and the card is still completed. Then `update_tasks { items: [{ taskId, complete: true }, …] }` for the approved batch cards not yet complete, and the debug card with them. Chained batch cards complete blockers first: a card cannot be completed while a blocker is incomplete, and entries apply in list order, so list every blocker before the cards it blocks. Read `results` entry by entry: a refused entry does not undo the others. A refusal on a blocker outside the batch: name it and stop that card.
2. **Reconcile the statuses (the checklist).** Each row is checked against its live value and written only if different. One read immediately before each card or note write (`get_task`, or the note through bandit:notes).

   | Where | Field | Becomes |
   |---|---|---|
   | Batch cards | completed, Execution column | Done (step 1). Sub-tasks all ticked. `stage/ready` stays: stage has no done value |
   | The sprint | status | `manage_sprints { action: "move", status: "closed" }` from `debugging` (or `executing`), only once every card is complete and nothing open blocks it (a refusal names what is open). Closed is final |
   | Ledger | Plan steps, Waves | Every row done, each with its evidence |
   | Ledger | Status line | `Closed {date}: {n} of {n} cards delivered and tested by the user` |
   | The sprint | papers link | In the vault, after step 3, the archived folder's path (`manage_sprints { action: "update", papersUrl }`: a Closed sprint still takes it); on the app's Notes it stays as written, since the papers stay where they are |
   | Handover report | Targets section | The sprint's table from `sprint_targets.py` without `--wave` (`references/templates.md` → Sprint targets), left out when no target is approved; a missed target is already a Lesson |
   | The project's sprint data file | Rows of this sprint | Rebuilt from the sprint records before the archive (`references/templates.md` → Sprint data); the archive keeps the rows, only their `where` changes at the next rebuild |
   | Ledger | Decisions log | The user's quoted approval and date, what shipped, what carried over, where the report lives, lessons |
   | Ledger, At a glance | Current wave, Next action, Handover report, Last update | "Sprint closed", "none", FINAL, today |
   | Ledger, Waves and cards | Status per card | `Tested by the user` |
   | Ledger | Milestone log | One line: close date, approval quoted, cards completed |
   | Handover report | Status marker | FINAL, with the regression list filled or marked "not run" with the reason |
   | Every paper (plan, briefs, ledger, prompt, review record, reports) | `status` | On the app's Notes `archived` (step 3); in the vault `done`, stamped in step 3 together with the archive stamps |

3. **Archive the sprint's papers through bandit:notes**, applied without a question: running `close` with every approval line ticked is the go (precondition 3); the report lists what was archived. Briefs, report, wave report and ledger go with them (the wave report's Lessons and Flow trend stay readable for later plans), and the sprint's WBS and any leftover the sprint consumed outside its papers (an inbox draft, a superseded copy) are archived in the same step. Ledger edits in step 2 are made **before** the archive, so the archived copy is final.
   - **On the app's Notes:** every note on the project's board with the tag `sprint-{name}` (`notes_list` of the board) is set to `archived` with `notes_set_status` and read back, and so is the sprint's WBS note (`{project}-sprint-{name}-wbs`, the note the vault bullet names: it carries no sprint tag, so it is found by its title on the project's board). The notes stay in place, out of the lists and the search; `notes_list` with `archived: true` reads them, which is how later plans read the Lessons. The sprint map and the data file stay in `.sprint/`: data files, not notes.
   - **In the vault:** folder `Projects/{slug}/sprint-{name}/` moves to `_archive/Projects/{slug}/sprint-{name}/`, every note stamped `status: done`, `archived-from` and `archived`, mirror folders moved with it; the sprint map goes with it, and the sprint's WBS (`Projects/{slug}/planning/{project}-sprint-{name}-wbs.md`) is archived in the same step.
4. **Verify.** Run `python3 ${CLAUDE_SKILL_DIR}/scripts/check_sprint.py --closed {name}` on a notes file built after the archive (`plan.md` → Closed-sprint check) and show its OK (SP15 fails while a paper or the WBS note of a closed sprint is not archived). Not OK, or "could not read the notes file": the sprint is not reported closed; run the archive again for what is still not archived. On the app's Notes: `notes_list` of the board shows no note with the sprint's tag and `notes_list` with `archived: true` shows every paper; one left out is archived again before the sprint is reported closed. Re-read live state and show it: `get_sprints { sprintId }` (status `closed`, every card completed), the ledger (every row done, Status and Decisions log filled), where the papers are (vault: the folder under `_archive/`, nowhere else, and one archived note's frontmatter; app: one archived paper read back with its status and tag). Any row still wrong is fixed or reported, not skipped.
5. **Report.** Ten lines at most: cards completed, on the app's Notes the conclusions written (each card skipped or refused named, with why), the debug card's Process lines (how many, how many fixed or turned into a lesson, any still open), sprint closed, statuses reconciled, papers archived, what stays open (push, deploy, production audits, `CLAUDE.md` corrections) and the line to restore if needed. Open items go in the report's Needs the user list and the final message, so they stay visible after the archive.

## Never

- Complete a card whose approval line is open, unless the user approved it or confirmed it tested in this chat; or infer approval from the debug result.
- Tick the approval line of a card the user has not approved in this chat, or complete a card whose approval line is still open.
- Ask for an approval or an archive yes when every approval line is ticked.
- Write a status that is already correct, or overwrite a card or note without reading it first.
- Delete anything. An archive can be reversed (bandit:notes `restore`).
- Archive before the cards are complete, or close the sprint before its cards and blockers are complete.
- Commit to the repository: code, tests, docs and notes in the repo are done before the release (precondition 5). Close only does bookkeeping: cards, sprint, ledger, archive.
- Merge into the deploy branch or deploy: that is `release`, on the user's deploy word. Close does not push; execution and debug push `development`, and close only reports whether it is level with origin.
