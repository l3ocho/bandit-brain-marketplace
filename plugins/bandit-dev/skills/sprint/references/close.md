# 🏁 The close cycle

Part of `bandit-dev:sprint`. Read before running `/bandit-dev:sprint close {sprint}`. Run only after debug and release are done. Archive rules are owned by bandit:notes (status `archived`, `references/storage-app.md` → Archive, restore, delete); completion rules by bandit:tasks. Where a sprint's papers are: `references/templates.md` → Papers.

Contents: Preconditions · Steps · Never

## Preconditions

Check all, report any miss as a fix row, and stop:

1. Ledger "At a glance" says debug is done and no row is open (or debug never ran and the user says so: record that).
2. **The debug card** (`Debug card:` in the ledger), when there is one, has every issue line ticked (`Expected:`, `Found:`, `Process:`); an unticked line refuses the close and is named. **The sprint's shape** (`references/templates.md` → Check lines): its ledger says `Approvals: debug card`, or it is an old-shape sprint.
   - **Its ledger says `Approvals: debug card`:** every build card is completed, delivered by its wave; a build card still open refuses the close and is named with its open lines (it is delivered by a wave or a debug row, never by close).
   - **An old-shape sprint:** every batch card is in `standby`, or already complete (the user may have completed some by hand: that is fine, close is idempotent). None has an open sub-task, except an open approval line (precondition 3). Any other open sub-task: name it.
3. **The user's approval.** A card whose approval line the user has ticked is approved: they tick it once they have tested it (`references/templates.md` → Approval line; the lines sit on the debug card, or on each batch card in an old-shape sprint), and running `close` is then the go for every step below, the archive included, with no question. Record it in the ledger as `Approval line ticked by the user` with the date read. An approval line that is open refuses the close and is named, unless the user approves that card, or says they tested it, in this chat, in their own words: name those cards once, and quote the answer in the ledger. A line ending `(rejected: new card {id})` is ticked on the user's word, quoted in the ledger. In an old-shape sprint a card left open stays open and is never completed. The user stops or changes the close by saying so.
4. **Release, the user's option.** The ledger has a `Released:` line (written by `release`), or the sprint closes with no app release: then write `Release: deferred` in At a glance (the next release covers it, `release.md` → Covering), add one Milestone log line saying the same, and say so in the report. **A sprint that changed the helpers** (Marketplace cards) still needs the plugin release before it closes: no plugin version in a `Released:` line → refuse and give the paste for `release`.
5. **Close makes no commit.** A released sprint: after `git fetch`, `git rev-list --count origin/{branches.deploy}..origin/{branches.trunk}` and the same for the local trunk print `0`. Anything else is refused, naming the commits (`git log --oneline`): they go to a new release or a card for a later sprint, never into this close. A sprint with `Release: deferred` skips this check.
6. **The sprint is not cancelled.** A sprint cancelled in the app (status `cancelled`) has nothing to close: say so, archive its papers as in step 3 on the user's yes, and run step 4's check with its name in `--closed`. A paused sprint is resumed first (`references/execute.md` → Run state).
7. Nothing needs the user that blocks closing. The ledger's needs-the-user list is read to them once; items for deploy, or a push that failed, stay open and go to the report (step 5), they do not block.

## Steps

Read the live state first (`get_sprints { sprintId }`, `get_task` for every card, the ledger, the report). **Every step checks before it writes: a state already correct is left alone and reported as "already done".**

0. **Cards that do not close (detached or carried, or, in an old-shape sprint, not approved in this chat), first:** the app refuses to close a sprint holding an open card, and a Closed sprint takes no change. For every batch card that stays open (one detached to the next sprint, or one that waits for a trigger): take it out of the sprint (`manage_sprints { action: "remove_card", replanConfirmed: true }`: the app asks before a running sprint's cards change, and running `close` is the go, so no question; the sprint goes into replanning, from debugging back to executing), leave it in Backlog, and write "detached" on its ledger row. **Then merge everything the sprint knows about it into its brief, before the archive**: what the plan, ledger and report say about the card (state, remaining steps, findings, decisions, acceptance-to-proof) in a closing section of the brief, which keeps its title so the card's `Brief:` line still resolves. One document per card, and it leaves this sprint's papers so the archive does not take it: it stays linked to its card and loses this sprint's tag (the next `plan` gives it that sprint's tag). The checker skips a detached card (SP2) and fails a second brief for the same card (SP6). **Once every such card is out,** approve the new plan in the same step: `manage_sprints { action: "approve_plan", sprintId }`, read back with `runState` `running` (the sprint is now `executing`, and the move to `closed` from `executing` is the one skip), and one Milestone log line naming the cards taken out.
1. **Tick the approval line, then complete the cards.** First, for each card the user approved in this chat, or rejected with its new card filed (precondition 3), with their words quoted in the ledger, `manage_subtasks { action: "tick", subtaskId, completed: true }` on its approval line (on the debug card, or on the card itself in an old-shape sprint), then read the card back. In an old-shape sprint a card whose approval line is open is not completed and goes to step 0; a card from a sprint planned before the approval line existed has none and closes as before. Next, unless the project's Project Context says `notes: none`, **each batch card's conclusions go into its linked note** (bandit:notes `references/conclusions.md`), unattended: running `close` is the go for those note writes, the cards' descriptions are left as they are, and a card with no linked note, two of them, or one still in the Inbox gets nothing written and is named in the report (step 5); a refused write is reported and the card is still completed (in a sprint whose ledger says `Approvals: debug card` the build cards are completed already, and their conclusions are written all the same). **Size the debug card** (`references/templates.md` → Debug card, Size): `update_tasks` with its `effort` from the count of its `Expected:` and `Found:` lines and `complexity` 1 (Simple), read back, and the size line under the wave report's Debug table. Then `update_tasks { items: [{ taskId, complete: true }, …] }` for the approved batch cards not yet complete (an old-shape sprint), and the debug card with them, last. Chained batch cards complete blockers first: a card cannot be completed while a blocker is incomplete, and entries apply in list order, so list every blocker before the cards it blocks. Read `results` entry by entry: a refused entry does not undo the others. A refusal on a blocker outside the batch: name it and stop that card.
2. **Reconcile the statuses (the checklist).** Each row is checked against its live value and written only if different. One read immediately before each card or note write (`get_task`, or the note through bandit:notes).

   | Where | Field | Becomes |
   |---|---|---|
   | Batch cards | completed, Execution column | Done (at delivery; an old-shape sprint: step 1). Sub-tasks all ticked. `stage/ready` stays: stage has no done value |
   | The debug card | effort, complexity, completed | The size the table gives (step 1), complexity Simple; every line ticked; Done |
   | Wave report | Debug section | Its table, a column per cause, and the size line under it |
   | The sprint | status | `manage_sprints { action: "move", status: "closed" }` from `debugging` (or `executing`), only once every card is complete and nothing open blocks it (a refusal names what is open). Closed is final |
   | Ledger | Plan steps, Waves | Every row done, each with its evidence |
   | Ledger | Status line | `Closed {date}: {n} of {n} cards delivered and tested by the user` |
   | Handover report | Targets section | The sprint's table from `sprint_targets.py` without `--wave` (`references/templates.md` → Sprint targets), left out when no target is approved; a missed target is already a Lesson |
   | The project's sprint data file | Rows of this sprint | Rebuilt from the sprint records before the archive (`references/templates.md` → Sprint data); the archive keeps the rows, only their `where` changes at the next rebuild |
   | Ledger | Decisions log | The user's quoted approval and date, what shipped, what carried over, where the report lives, lessons |
   | Ledger, At a glance | Current wave, Next action, Handover report, Last update | "Sprint closed", "none", FINAL, today |
   | Ledger, Waves and cards | Status per card | `Tested by the user` |
   | Ledger | Milestone log | One line: close date, approval quoted, cards completed |
   | Handover report | Status marker | FINAL, with the regression list filled or marked "not run" with the reason |
   | Every paper (plan, briefs, ledger, prompt, wave notes, review record, reports) | `status` | `archived` (step 3) |

3. **Archive the sprint's papers through bandit:notes**, applied without a question: running `close` with every approval line ticked is the go (precondition 3); the report lists what was archived. Briefs, report, wave report and ledger go with them (the wave report's Lessons and Flow trend stay readable for later plans), and the sprint's WBS and any leftover the sprint consumed outside its papers (an inbox draft, a superseded copy) are archived in the same step. Ledger edits in step 2 are made **before** the archive, so the archived copy is final.
   - Every note on the project's board with the tag `sprint-{name}` (`notes_list` of the board) is set to `archived` with `notes_set_status` and read back, and so is the sprint's WBS note (`{project}-sprint-{name}-wbs`: it carries no sprint tag, so it is found by its title on the project's board). A plan linked to a card stays at its card's state: Done once its card is done, and the app refuses to archive it (`PLAN_FOLLOWS_CARD`); it is left Done, and SP15 counts it settled. The notes stay in place, out of the lists and the search; `notes_list` with `archived: true` reads them, which is how later plans read the Lessons. The sprint data file stays in `.sprint/`: a data file, not a note. The app's sprint page keeps the sprint's map.
4. **Verify.** Run `python3 ${CLAUDE_SKILL_DIR}/scripts/check_sprint.py --closed {name}` on a notes file built after the archive (`plan.md` → Closed-sprint check) and show its OK (SP15 fails while a paper or the WBS note of a closed sprint is not archived). Not OK, or "could not read the notes file": the sprint is not reported closed; run the archive again for what is still not archived. `notes_list` of the board shows no note with the sprint's tag (other than a plan linked to a done card, status Done) and `notes_list` with `archived: true` shows every paper; one left out is archived again before the sprint is reported closed. Re-read live state and show it: `get_sprints { sprintId }` (status `closed`, every card completed), the ledger (every row done, Status and Decisions log filled), where the papers are (one archived paper read back with its status and tag). Any row still wrong is fixed or reported, not skipped.
5. **Report.** Ten lines at most: cards completed, the debug card's size and its causes, the conclusions written (each card skipped or refused named, with why), the debug card's Process lines (how many, how many fixed or turned into a lesson, any still open), sprint closed, statuses reconciled, papers archived, what stays open (push, deploy, production audits, `CLAUDE.md` corrections) and the line to restore if needed. Open items go in the report's Needs the user list and the final message, so they stay visible after the archive.

## Never

- Close with an approval line open, or complete a card whose approval line is open, unless the user approved it or confirmed it tested in this chat; or infer approval from the debug result.
- Tick the approval line of a card the user has not approved, or rejected, in this chat; reopen a completed build card.
- Ask for an approval or an archive yes when every approval line is ticked.
- Write a status that is already correct, or overwrite a card or note without reading it first.
- Delete anything. An archive can be reversed (bandit:notes `restore`).
- Archive before the cards are complete, or close the sprint before its cards and blockers are complete.
- Commit to the repository: code, tests, docs and notes in the repo are done before the release (precondition 5). Close only does bookkeeping: cards, sprint, ledger, archive.
- Merge into the deploy branch or deploy: that is `release`, on the user's deploy word. Close does not push; execution and debug push `development`, and close only reports whether it is level with origin.
